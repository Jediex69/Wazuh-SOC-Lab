# Windows Service Startup Changes — SOC Event Analysis

## 1. Objective

Analyze a sequence of Windows events detected by Wazuh involving changes to Windows service startup types.

The objective was to practice a basic SOC investigation workflow:

* Identify and classify the alert.
* Examine the underlying Windows event.
* Analyze the affected services and event context.
* Correlate events occurring within a short time window.
* Determine whether there is sufficient evidence of malicious activity.
* Document investigation limitations and the final assessment.

---

## 3. Initial Detection

Wazuh generated multiple alerts with:

* **Rule ID:** `61104`
* **Description:** `Service startup type was changed`
* **Rule level:** `3`
* **Windows Event ID:** `7040`
* **Provider:** `Service Control Manager`
* **Channel:** `System`

The initial assumption was not to treat the alert as a security incident automatically. A service startup configuration change can be legitimate system activity, so additional context was required.

---

## 4. Event Analysis

Several Event ID 7040 events were detected within approximately half a second.

The observed changes included:

### TrustedInstaller

Several events showed changes between:

```text
On-demand → Automatic
Automatic → On-demand
```

The affected service was:

```text
Windows Modules Installer
```

associated with:

```text
TrustedInstaller
```

### BITS

One of the events involved:

```text
Background Intelligent Transfer Service (BITS)
```

with a change from:

```text
On-demand → Automatic
```

The events were generated by the Windows Service Control Manager.

## 6. Secondary Event Investigation

The event immediately preceding the service changes was also investigated.

### Windows License Activation Failure

Relevant fields:

```text
Event ID: 8198
Provider: Microsoft-Windows-Security-SPP
Channel: Application
Severity: ERROR
Wazuh Rule: 60646
Wazuh Level: 5
Action: AutoActivate
Trigger: UserLogon
Process: slui.exe
```

The event indicates that Windows attempted an automatic license activation during user logon and the activation failed.

The event contained:

```text
hr=0x87E10BC6
```

The available telemetry did not provide sufficient information to determine the exact reason for the activation failure.

---

## 7. Correlation Analysis

The license activation event and the service startup changes occurred close together in the Wazuh timeline.

However, no direct causal relationship was established.

The license activation event belonged to the **Application** channel and had:

```text
eventRecordID = 228
```

The service startup events belonged to the **System** channel and had event record IDs:

```text
387
388
391
394
395
396
```

Because these are different Windows event channels, their `eventRecordID` values cannot be used as a direct cross-channel correlation mechanism.

The missing record IDs between the observed System events were also not found in the Wazuh alert data. This does not prove that those events did not exist in Windows; it only means that corresponding events were not available in the Wazuh data being queried.

---

## 8. Assessment

### Classification

**System / configuration activity**

### Security assessment

No sufficient evidence of malicious activity was identified in the available telemetry.

The observed events involved legitimate Windows components such as:

* Windows Modules Installer / TrustedInstaller
* Background Intelligent Transfer Service (BITS)
* Windows Search
* Microsoft Software Protection Platform

The rapid sequence of service configuration changes warranted investigation, but the available data did not demonstrate malicious execution, persistence, or compromise.

---

## 9. Limitations

The investigation highlighted a visibility limitation in the current lab.

The collected events showed **what changed**, but did not provide enough process-level context to confidently determine the exact origin of each service configuration change.

In addition, not every Windows event was necessarily available in the Wazuh alert index.

This means that the investigation could not reconstruct the complete sequence of Windows activity.

Further telemetry, such as process creation monitoring, could provide additional context in future exercises.

---

## 10. Response

No containment or remediation action was performed.

This was intentional.

There was insufficient evidence to justify modifying the Windows configuration, stopping services, isolating the endpoint, or treating the activity as a security incident.

The investigation was closed with no evidence of malicious activity based on the available telemetry.

---

## 11. Lessons Learned

This investigation demonstrated several important SOC concepts:

* A Wazuh alert does not automatically represent a security incident.
* `rule.level` represents the severity assigned to the Wazuh rule; it is not equivalent to incident severity or CVSS.
* Windows Event ID 7040 indicates a service startup configuration change.
* Multiple alerts occurring close together should be investigated as a sequence rather than automatically treated as separate incidents.
* Temporal correlation does not establish causality.
* `eventRecordID` values from different Windows event channels should not be directly correlated.
* Lack of evidence is not evidence of malicious activity.
* Telemetry limitations must be explicitly documented during an investigation.

---

## 12. Conclusion

The investigation identified a burst of Windows service startup configuration changes involving legitimate Windows services.

The available evidence was insufficient to classify the activity as malicious.

The case was therefore documented as **system/configuration activity with no evidence of compromise**, while identifying the lack of process-level telemetry as an area for future improvement.

This exercise demonstrates a basic SOC workflow using Wazuh:

**Alert → Triage → Event Analysis → Temporal Correlation → Assessment → Documentation**
